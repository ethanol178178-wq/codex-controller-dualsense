# Signing setup and release checklist

This document separates the one-time account work from the automated release
workflow. Do not place passwords, one-time codes, private keys, or SignPath API
tokens in issues, commits, screenshots, or chat messages.

## One-time maintainer steps

1. Enable multi-factor authentication on GitHub and SignPath.
2. Read the [SignPath Foundation conditions](https://signpath.org/terms.html)
   and submit the [open-source application](https://signpath.org/apply.html).
3. During review, provide the public repository, release page,
   [`CODE_SIGNING_POLICY.md`](CODE_SIGNING_POLICY.md), [`PRIVACY.md`](PRIVACY.md),
   and the project's license and third-party notices.
4. After approval, install the SignPath GitHub App and grant it access only to
   this repository.
5. Enable branch protection or a repository ruleset that blocks force pushes
   and requires CODEOWNERS review where the team structure allows it.
6. In the SignPath project, create two artifact configurations:
   - **Portable:** the GitHub artifact is a ZIP; sign only
     `DualSenseCodex/DualSenseCodex.exe` inside it.
   - **Installer:** the GitHub artifact is a ZIP; sign only
     `DualSense-Codex-Setup-<version>.exe` inside it.
7. Both artifact configurations must accept a `version` parameter and enforce
   `ProductName = Codex Controller for DualSense` plus the matching product and
   file version. Configure a trusted timestamp.
8. Add the following GitHub Actions repository configuration:

| Kind | Name | Value |
| --- | --- | --- |
| Secret | `SIGNPATH_API_TOKEN` | SignPath token for a submitter account |
| Variable | `SIGNPATH_ORGANIZATION_ID` | Organization ID from SignPath |
| Variable | `SIGNPATH_PROJECT_SLUG` | Approved SignPath project slug |
| Variable | `SIGNPATH_SIGNING_POLICY_SLUG` | Release signing policy slug |
| Variable | `SIGNPATH_PORTABLE_ARTIFACT_CONFIGURATION_SLUG` | Portable artifact configuration slug |
| Variable | `SIGNPATH_INSTALLER_ARTIFACT_CONFIGURATION_SLUG` | Installer artifact configuration slug |

The release workflow intentionally fails before publishing when any value is
missing. Never replace the secret with a plain repository variable.

## Per-release checklist

1. Review all code, dependency, packaging, workflow, policy, and release-note
   changes on the default branch.
2. Run the complete automated test suite and perform the documented Windows and
   DualSense hardware checks.
3. Update `VERSION`, `CHANGELOG.md`, and `RELEASE_NOTES.md` together.
4. Create and push the matching `v<version>` tag.
5. Inspect the portable signing request in SignPath, compare its GitHub source
   and workflow run, then approve it manually.
6. After the installer is built, inspect and manually approve the installer
   signing request.
7. Confirm that the GitHub release contains the installer, portable ZIP, and
   checksum file generated by the same workflow run.
8. Download the public files on a clean Windows computer and verify install,
   uninstall, startup, controller connection, and SmartScreen presentation.

## Local verification

Run this on the downloaded executable and installer:

```powershell
Get-AuthenticodeSignature .\DualSenseCodex.exe | Format-List Status,StatusMessage,SignerCertificate,TimeStamperCertificate
Get-AuthenticodeSignature .\DualSense-Codex-Setup-<version>.exe | Format-List Status,StatusMessage,SignerCertificate,TimeStamperCertificate
Get-FileHash .\DualSense-Codex-Setup-<version>.exe -Algorithm SHA256
```

`Status` must be `Valid`, a signer and timestamp authority must be present, and
the SHA-256 value must match the release checksum file. A valid signature proves
artifact integrity and publisher identity; it does not replace malware scanning
or release testing.
